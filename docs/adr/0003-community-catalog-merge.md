# 运行时多源合并社区清单，修订「单一 registry 整体覆盖」

0.5.0 起 dsh-m 的市场视图改为双层：主清单（包内 registry.json 或 registryUrl 自定义覆盖源，§2.1–2.4 全部语义不变）之上叠加只读的社区清单（awesome-dsh-plugin 全量社区目录，经 npm 包 `dsh-plugin-catalog` 版本化分发），合并展示、主清单恒优先。这修订了 0.4.0 定稿的 Q25「单一 registry 地址整体覆盖、不做运行时多源合并」——该决策针对的是当时「个人策展清单」的单源形态；owner 确认 dsh-m 向全量社区目录形态靠拢后，纯覆盖模型无法同时表达「我的精选」与「社区全量」两层，覆盖会把其中一层整体顶掉。

## Considered Options

- **维持单源覆盖**：社区清单只能作为又一个 registryUrl 候选，用户在「我的精选」与「社区全量」之间二选一切换——与 0.5.0 产品方向（合并展示、可关闭社区层）直接冲突。
- **在 awesome 仓库产出 dsh-m 形状的衍生 JSON**：消费端最薄，但翻译规则（id 合成、子包跳过）被锁进生产端 CI，dsh-m 每调一处规则都要动上游仓库；且 plugins.json 已是 dsh-market、dsh-find-plugin 等多端共读的 canonical 数据，再造一个衍生格式制造第二事实源。
- **消费端目录适配层（采纳）**：dsh-m 拉原生 `plugins.json`（锚定 npm 包，版本号即 revalidate 验证器），在消费端做 id 合成、来源归一与分类开放集；翻译规则随 dsh-m 独立演进，上游 schema 演进（加字段、裂变分类）不要求 dsh-m 发版。

## Consequences

- registry 层出现两种校验语义并存：主清单严格（未知字段/脏条目整份拒绝）、社区清单容器严格 + 条目宽松（脏条目跳过计数）。消费者必须区分两层来源，`RegistryState` 需要携带独立的社区状态摘要。
- 社区清单不做包内快照：探测失败时回落**运行时缓存**并以显式 stale 标注呈现（市场页可见「缓存快照」，不冒充 ready）；「陈旧即错误」约束的是绝不让过期数据冒充最新，主清单的包内快照兜底语义不变。（2026-10-02 修订：0.9.15 起 SWR 常态化——先回缓存后台自愈是设计常态态，市场页不再显示临时横幅；stale 标注移至设置页社区卡，「不冒充 ready / 陈旧可被观察到」不变。）
- 分类类型系统从封闭 5 值变为「精选 5 + 社区开放集」，`categoryCounts`、筛选栏与 `dshm_search` 的 category 参数都要按开放集处理。
- 上游 npm 包发布管线冻结时社区层随之冻结（同一条 CI 产出 Pages 与 npm 包）；版本号与 `fetchedAt` 必须可见，让陈旧可被观察到。
