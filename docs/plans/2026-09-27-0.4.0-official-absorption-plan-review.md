## 二、阻断级问题（必须先修计划，否则执行会卡死或做错）

### A1. Task 9「精确放行」的架构落点错了：needs-builds 拦截根本不在 profile-transaction.ts

**计划说**（plan L210-222）：Modify `src/core/profile-transaction.ts`；「needs-builds 分类命中 → 读 pnpm-workspace.yaml → readPendingBuilds 非空 → applyPreciseBuilds 写回 → 重跑」。全局 Modify 清单（plan L55-73）**不含 `src/core/dsh-cli.ts`**。

**仓库现实**：needs-builds 的拦截与全量放行都发生在 `src/core/dsh-cli.ts` 的 `makeAddViaLadder`（L632-682）：`add` 被 prepare 拦 → `writeDangerouslyAllowAllBuilds`（L383-396）→ 重试 → 成功即返回 `{class:'ok', usedAllowAllBuilds:true}`。**事务层 `installNpm`（profile-transaction.ts L676）从 `runner.add` 永远只能看到 ok 或失败类，看不到 needs-builds**——DESIGN.md §3 明文「在途重试在 adapter 的 makeAddViaLadder 内耗尽」。照计划在 profile-transaction.ts 里等「needs-builds 分类命中」，等不到；执行者会发现计划与现实不符而停摆（执行纪律会触发，但整个 Task 9 白排）。

**修法（推荐方案 1，改动最小）**：
- 精确放行嵌进 ladder：`makeAddViaLadder` 的 `allowAllBuilds` 注入点升级为「build-approval 决策回调」——prepare 被拦时先 `readPendingBuilds`，非空 → `applyPreciseBuilds` 逐键写 → 重试；空/不可读 → 既有 `withDangerouslyAllowAllBuilds` 兜底。`src/core/dsh-cli.ts` 与 `tests/pnpm-outcome.test.mjs` 必须进 Task 9 的 Files（以及全局 Modify 清单）。
- `RunnerOutcome.usedAllowAllBuilds: boolean`（dsh-cli.ts L261）必须同步进化为携带 `buildApprovals: string[]` + `fallbackAllBuilds: boolean`（或等价形状），否则事务拿不到「放行了谁」，Task 9 的 CommittedResult 新字段无从填起。
- Task 9 的接口契约与测试面相应重写（fake runner 桩的返回值形状也要改）。
- 方案 2（runner 裸 add、needs-builds 上抛给事务接阶梯）不推荐：破坏「adapter 内耗尽」的既有设计决策，改动面更大。
- 附注（风险声明即可，不必加锁）：官方 `approveBuilds` 的调用前提是「caller 持 profile manifest 锁」（官方 docstring 原文）。dsh-m 事务只有进程内 FIFO，无跨进程文件锁；与官方 UI 并发安装时 `pnpm-workspace.yaml` 存在写竞态窗口。低概率，但在计划里写一句已知风险与「遇 `stale-approval` 类失败即整单失败回滚」的处置即可。

## 三、高优先级问题（动手前应修，不修会返工或卡壳）

### B1. `PROTECTED_MODULES` 硬编码名单是官方 16 项的 10 项子集，且未写子集标准

计划（plan L142）列 10 项；官方 `protectedModules`（plugin-manager L1077-1092）实为 **16 项**，计划漏掉：`@deepseek-ai/dsh-client-ui-settings-plugin-inventory`、`@deepseek-ai/dsh-client-ui-plugin-manager`、`@deepseek-ai/dsh-host-plugin-inventory`、`@deepseek-ai/cordis-plugin-timer`、`@deepseek-ai/dsh-host-frontend-static`、`@deepseek-ai/dsh-hmr`。

本机 profile 依赖里目前确实没有这些包（现实风险低），但后果不对称：**委派路径官方 16 项全覆盖，降级/CLI 路径只有 10 项**——`dshm uninstall @deepseek-ai/dsh-hmr`（若未来进了 profile）会放行。镜像 16 项的边际成本为零。
**修法**：逐字镜像官方 16 项 + 注释锚点（`dsh-plugin-manager@0.1.7-rc.2 lib/index.js L1077`），并在「升级后必查」口径里加一条「DSH 升级后 diff 官方名单」；或在计划里写明子集取舍标准。另注意官方名单是动态防御（含 ownerEntryId 自保护），dsh-m 的 `'dsh-m'` 自保护在委派前先行判定（plan Task 5 ② 在 ③ 之前）——这个顺序是对的，保持。

### B2. 委派路径的 `applied:'live'` 判定机制与错误映射未钉住

计划 Task 5：`PluginManagerLike.setPluginEnabled(...): Promise<unknown>`，「applied:'live'（委派结果带 restart-required 语义时如实透传）」。官方 setPluginEnabled 返回 change() 的富结果（含 warnings、可能的 `"overridden"` 结果），`unknown` 拿不到可判定的信号——执行者只能猜。
**修法（二选一，写进 Task 5 契约）**：(a) 委派调用后**复读 `listPlugins()` 行**，以 `enabled`/`fiberPhase` 实际变化判定 `applied`；(b) 钉住官方返回形状的最小投影字段。同时补一行映射表：官方 `readOnlyReason === 'management-required'` → `ToggleError('protected')`、`'unaddressable'` → `ToggleError('unaddressable')`（计划只写「抛对应 ToggleError」，枚举值不写执行者要去翻官方源码）。

### B3. Task 19 `verified` 填值依据的指针不准：008 §3 里没有版本号

计划 Consumes（plan L361）称「008 文档的实测记录 §3」。实际 008 §3 是「升级后必查清单」——一张**文案核对的索引表**，每行的「对照源」列指向各插件仓库的 README 徽章 / `docs/COMPATIBILITY.md`；**实测版本号的真值在那里，不在 008 本身**。执行者若只读 008 会找不到可填的值。
**修法**：Task 19 Consumes 改为「008 §3 五条目各自的对照源（各仓库 README / COMPATABILITY.md）提取实测代际」，并显式写明 5 条目集合（skip-browser-auth / surf / copilot-auth / skins / dsh-m），**obmc-web 不在其列，不要多填**。

### B4. Task 17 视图模型相位映射内部矛盾

计划（plan L331）：`pending/disabled→idle`、`null→''`。但 `LivePhase` 联合类型里**没有 `'disabled'`**——disabled 的外在表现恰恰是 phase 为 null（fiber undefined），两行映射打架。
**修法**：相位点只映射 phase 五值（active→ok、failed→err、pending→idle、loading/unloading→busy、null→''）；「已停用」的表达归 Switch 控件状态（switchOn=false）而非相位点，或明写「enabled===false 时相位点固定 idle、phase 判定不参与」——选一个，别让两个输入源都 claim 同一个 dot。

## 四、建议项（执行中处理即可，但写进计划更稳）

- **C1**（Task 1）：`@deepseek-ai/dsh-atomic-write@0.1.7-rc.2` 有硬 peer `@deepseek-ai/cordis: ~4.0.4`（无 peerDependenciesMeta，实现本身纯 fs 不依赖 cordis）。仓库 devDeps `^4.0.1` 可被 4.0.x 高版满足（npm 可解）；但 dsh-m 作为插件装入 profile 时（profile `autoInstallPeers: false`）pnpm 会报 unmet peer 警告。Task 1 Expected 补一句「unmet peer 警告不算失败；ERESOLVE 硬错则停下报告」。
- **C2**（红线）：本机 profile 的 `cordis.patch.yml` 含**真实 apiKey**（评审中已亲眼确认）。Task 2/4 的「本机实态样本」必须使用脱敏的结构等价 fixture，**禁止把生产 profile 文件原样拷进 `tests/`**。Task 20 的脱敏终审只覆盖 README，建议执行纪律补一句「测试 fixture 同样过脱敏」。
- **C3**（Task 4）：CLI 无 loader 形态下，「已装但不在 bundles、也无补丁层」的插件（Task 10 的 no-patch-layer 纯依赖形态）enabled 推断会得到 false 且无 lockReason——这是「未装载」不是「被关」。补一行：该形态输出 `lockReason:'no-entry'`（toggleable=false）。
- **C4**（Task 5 契约笔误）：现有签名是 `setLivePluginDisabled(pkg, disabled)`（live-plugin.ts L28，第二参是 disabled），计划写成 `(pkg, enabled)`。改为调用点传 `!enabled`，或在契约里写薄包装 `setLivePluginEnabled(pkg, enabled) = setLivePluginDisabled(pkg, !enabled)`。
- **C5**（Task 16 验证环境）：`node lib/cli.js toggle dsh-m off` 虽因保护门不落盘而安全，但 dev 期一切 CLI toggle 冒烟统一 `DSH_HOME=<dev-home>` 隔离（env.ts 原生支持），与「最终验证」的避生产 profile 口径对齐。
- **C6**（交接前置）：git 工作区当前有 **staged 未提交**的 `CONTEXT.md`（M）+ 两份 ADR（A）+ 计划本身（A）。执行 agent 接手第一笔应先落一个 docs commit（如 `docs(0.4.0): plan, ADRs, context terms`），否则这些会混进 Task 2 的第一个 checkpoint commit。
- **C7**（顺带确认，无需动作）：Task 4 的 `LoaderEntry` 加宽方向正确——`disabled`/`fiber.state` 确为 entry 顶层字段（现接口把它们放在 `options` 下是历史误差，官方 readPluginInventory 读法为准）；`entry.options.name === pkg` 匹配与官方 `moduleName` 一致。
